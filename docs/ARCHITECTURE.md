# Kittine Architecture

Kittine is four independent pieces that compose through plain files and a
subprocess boundary — there's no shared in-memory state between them.

```
 App.kitty
     │  (text)
     ▼
┌─────────────────────┐
│  kittine-compiler    │  Rust CLI: lexer -> parser -> codegen
│  (kittine-compiler/) │
└─────────────────────┘
     │  (writes)
     ▼
   App.rs  ── "Generated by kittine-compiler. Do not edit by hand."
     │  (compiled by)
     ▼
┌─────────────────────┐
│  cargo + rustc        │  --target wasm32-unknown-unknown
└─────────────────────┘
     │  (produces)
     ▼
   App.wasm
     │  (post-processed by)
     ▼
┌─────────────────────┐
│  wasm-bindgen         │  --target web
└─────────────────────┘
     │  (produces)
     ▼
   pkg/*.js + pkg/*.wasm  ── browser-ready JS glue + processed wasm
     │  (served by)
     ▼
┌─────────────────────┐
│  vite-plugin-kittine  │  orchestrates the four steps above on each
│  (vite-plugin-kittine/) │  transform of a .kitty file, and serves the
└─────────────────────┘  result to the dev server / production bundle
```

## `kittine-compiler/` — the compiler

- **`lexer.rs`** — hand-written scanner. Always tries the longest matching
  multi-character token first (`<{`, `>>`, `</`, `/>`) before falling back
  to single characters, so e.g. `<{` is never accidentally split into `<`
  and `{`. Every token carries `line`/`col` so the parser can implement
  indentation-based blocks.
- **`ast.rs`** — plain data types (`Program`, `Import`, `Item` [`Component`
  or `Function`], `Stmt`, `Expr`, `JsxNode`) with no behavior.
- **`parser.rs`** — recursive-descent parser. The one non-obvious piece is
  how `if>` / `orif>` / `else>` blocks get delimited without braces: each
  block records the source column of its own keyword as `base_col`, then
  keeps consuming statements as long as the next statement's column is
  greater than `base_col`; a sibling `orif>` / `else>` is recognized
  because it sits back at exactly `base_col`. This is the same "off-side
  rule" technique Python's tokenizer uses for indentation, applied at
  parse time instead of lex time since only `if>` chains need it (`func`
  bodies stay brace-delimited).
- **`codegen.rs`** — walks the AST once, emitting Rust source as a plain
  `String` (no intermediate Rust AST/`syn` crate involved — this keeps the
  code generator simple and its output easy to eyeball-diff against the
  spec). Tracks which variable names have been declared so far in the
  current component to decide `let (x, set_x) = signal(..)` vs.
  `set_x.update(..)` for each `<{x}> >> ..`.
- **`main.rs`** — thin `clap`-based CLI wrapper around the three passes
  above, plus recursive `import` resolution: compiling a file that
  `import`s others also compiles each imported `.kitty` file (and anything
  *it* imports) to its own sibling `.rs`, tracking already-compiled files
  to avoid duplicate work and detecting import cycles as an error instead
  of recursing forever.

## `vite-plugin-kittine/` — the build integration

A single Vite plugin (`index.ts`) hooking `transform()` for any `.kitty`
module id:

1. Finds the Rust crate the file lives in (walks up for the nearest
   `Cargo.toml`).
2. Shells out to `kittine-compiler build <file>` synchronously.
3. Shells out to `cargo build --target wasm32-unknown-unknown` for that
   crate (skipped if nothing `.rs`/`.kitty`/`.toml`-relevant changed since
   the last build, tracked via `mtime`).
4. Shells out to `wasm-bindgen --target web` to produce browser-ready glue.
5. Returns a small JS module that re-exports the wasm-bindgen glue's
   `init` function, bindings, and named exports — so `import init from
   "./App.kitty"` in application code transparently gets the compiled
   component.

It also registers a dev-server middleware to serve the `pkg/` output
(the wasm-bindgen glue + `.wasm` binary) as static files, and tells Vite's
file watcher to ignore `target/` and `pkg/` so mid-build writes don't
trigger a spurious reload loop.

## `example-app/` — the reference integration

A Leptos CSR crate (`leptos = { version = "0.7", features = ["csr"] }`,
`leptos_router = "0.7"`) whose `main.rs` mounts the compiled `App`
component to `#[id="root"]` in `index.html`, and whose `vite.config.ts`
registers the plugin with zero configuration (it infers the crate root and
output directory automatically). `App` wraps `Home`/`About`/`NotFound`
pages in `leptos_router`'s `<Router>` — see
[LANGUAGE.md § Routing](LANGUAGE.md#routing) for why that needed no
compiler changes beyond bringing `leptos_router` into scope.

## `vscode-kittine/` — editor support

A standard TextMate-grammar-based VS Code extension (no language server).
See [VSCODE_EXTENSION.md](VSCODE_EXTENSION.md).

## Why this split?

Each piece is independently testable and replaceable:

- `kittine-compiler` has zero knowledge of Vite, Node, or the browser — it
  is a pure text-in/text-out CLI, exercised directly by `cargo test`
  (`kittine-compiler/src/tests.rs`) without needing a browser or WASM
  toolchain at all.
- `vite-plugin-kittine` has zero knowledge of Kittine's grammar — it only
  knows "run this CLI, then run cargo, then run wasm-bindgen." Swapping in
  a different frontend framework target, or a completely different
  compiler for a future Kittine version, doesn't require touching this
  file's structure.
- `vscode-kittine` has zero knowledge of either — it's pure syntax
  highlighting driven by a declarative grammar file.
